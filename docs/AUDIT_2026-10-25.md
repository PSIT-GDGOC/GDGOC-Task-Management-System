# Application audit — 25 October 2026

Reviewed the `main` source, the deployed Vercel login screen, Render readiness and
Google authentication endpoints, and the supplied Supabase project endpoint.
Functional changes are proposed on `fix/app-audit-auth-and-task-workflows`.
Production records, hosting settings, and the main branch were not changed.
Authenticated workflow testing used disposable accounts in a local PostgreSQL
container and the local frontend/backend. The Supabase dashboard and its policies
were not accessible through the supplied public project URL; database connectivity
was verified through the API readiness response.

## Verified findings fixed in this PR

Backend password-login findings apply when the existing development/staging login
endpoint is enabled. Normal production gating is retained. Local preview
impersonation affected frontend state; server authorization still required a valid session.

## Verification

- All workspace type checks and production builds pass under Node.js 22.
- Backend ESLint passes. API fixtures now authenticate with actual password hashes;
  application code has no test-only password bypass.
- `npm test`: 15 client, 3 admin, and 21 backend unit tests pass.
- Database/API integration: 87 tests pass against isolated temporary schemas in local PostgreSQL 16.
- Redis integration: 8 tests pass against a dedicated local Redis 8 container.
- Total: **134 passing tests**, including **28 added regression tests**.
- Browser: failed password login remains on the form with its error; owner assignment,
  member start/submission, owner approval, and persistence after refresh were checked locally.
- Added a frontend CI workflow for both frontends' type checks, tests, and builds.

## Deployment blockers and remaining work

1. **Live Google authentication is unavailable.** The deployed
   `/api/v1/auth/google/url?portal=member` returns HTTP 503 with
   `Google authentication is not configured`. Configure the club Google OAuth
   credentials/callback and allowed frontend origins before relying on Google login.
   This PR does not enable development login in production. Password sign-in remains
   on the existing development/staging endpoint and is disabled in normal production.
   Review the production authentication setup before deployment: legacy accounts
   without a password hash can no longer use the shared default password.
2. **Review existing grants and rotate existing predictable role keys.** This PR
   prevents new client-requested grants and shorthand-key fallback; it cannot prove
   whether existing grants were legitimate. Seeding retains existing keys deliberately.
   Owners can inspect and rotate them in the key vault after sign-in is configured.
3. **Some leader views still use sample team/profile content.**
   `LeaderOverview.tsx`, `TeamDetailPage.tsx`, and the team labels in analytics still
   depend on `data/mockData.ts`. Replace them with server directory data, especially
   before using custom teams. The task rows now use persisted task state.
4. **File storage, password recovery, and free-task claiming UI remain unfinished.**
   Password recovery is a notice rather than a working reset flow; file links in
   descriptions are the supported workaround. The API supports claiming tasks but
   the active member view focuses on assigned work.
5. **Six npm audit entries remain:** one high (`zod`) and five moderate
   (`react-router`, `react-router-dom`, `postcss-selector-parser`, `postcss-nested`,
   `tailwindcss`). Address these in a separately validated framework/schema upgrade;
   the suggested automatic fix includes major versions. No claim is made that these
   advisory entries are all reachable in the deployed browser app.
6. **Cross-site session behavior requires production browser verification.** Vercel
   and Render use different sites. Confirm HTTPS cookies, `SameSite=None`, exact
   origins, and supported-browser third-party-cookie behavior. A same-origin API
   proxy/custom-domain setup may be appropriate. Local workflow tests do not verify
   that production cookie configuration.

The Render readiness endpoint returned `ready`, with PostgreSQL and Redis both
connected. HTTP 404 at the supplied Supabase project root is not evidence of a
broken database; it is not an application homepage.
